# ADR-0008：固定工程目录与依赖方向

- 状态：Accepted
- 日期：2026-09-02
- 决策依据：[ADR-0001](0001-nextjs-modular-monolith.md) 与阶段 A 协作退出条件

## 背景

[ADR-0001](0001-nextjs-modular-monolith.md) 已确认 Next.js 全栈模块化单体及接口、应用、领域、基础设施四层职责，但尚未决定这些边界在仓库中的具体落点。多人开始工程骨架和业务模块后，如果仅依赖口头约定，Next.js 路由、业务用例、数据库访问、前端组件和生成代码很容易相互穿透，模块也会通过内部路径形成隐式公共接口。

工程目录必须同时满足 Next.js 的路由约定、服务端与客户端运行时隔离、业务模块独立所有权、契约优先和后续自动化边界检查，且不能通过建立多个部署包提前拆分一期单体。

## 决策

采用 [工程目录与依赖方向](../project-structure.md) 中定义的单应用、按业务模块纵向组织结构：

- `src/app` 只放 Next.js 路由入口、页面组合和 HTTP/SSE 传输适配；
- `src/modules/<module>` 按业务边界拥有 `domain`、`application`、`infrastructure`、`presentation` 和按需创建的公开入口；
- 每个模块的 `public/contracts.ts`、`public/server.ts`、`public/client.ts` 是跨模块访问的唯一合法入口；
- `src/bootstrap` 是服务端组合根，只组装模块公开能力与 `src/platform` 技术实现；
- `src/platform` 承载无业务所有权的技术能力，`src/shared` 只承载已经确认的纯共享语义和 UI；
- 根目录 `api/` 保存对外机器契约，`src/app/api/` 保存 Next.js 传输实现，两者不得混为同一职责；
- 模块单元测试邻近源码，全局 `tests` 只承载架构、HTTP/SSE 契约、集成与端到端测试；
- 可完整重建的派生代码放入 `src/generated`，不得进入领域、应用或公开契约；数据库迁移属于需审查的历史记录，不视为可丢弃生成代码；
- 跨模块依赖只能指向公开入口，必须单向、登记且无环；领域层不依赖框架、数据库或供应商，应用层不依赖基础设施具体实现；
- 工程骨架必须用自动化检查验证依赖、运行时与生成代码边界，并用一个真实纵向切片证明结构可用。

目录是职责约束，不要求预先创建空目录、空门面或虚构接口。具体校验工具、测试框架和代码生成器在工程基础工作包中依据实际技术栈选择，本 ADR 不锁定包或版本。

## 理由

纵向业务模块让同一工作包能够同时拥有领域、用例、实现、展示和测试，减少多人对全局分层目录的高频争用；模块内部继续保持四层依赖，使单体部署不会退化为任意互访。

为服务端、客户端和跨运行时契约设置不同公开入口，可以在代码评审与自动化检查中明确识别越界导入，降低数据库、密钥或供应商 SDK 被带入客户端模块图的风险。将 Next.js 路由保留为薄接口层，则能避免框架文件成为无法测试的业务逻辑容器。

## 替代方案

- 全仓按 `domain`、`application`、`infrastructure` 水平分层：层次直观，但不同业务模块的文件和所有权混在一起，跨模块内部引用难以识别，多人更容易修改同一目录。
- 全部代码就近放入 `src/app`：符合框架共置能力，但路由布局与业务边界耦合，HTTP、页面、持久化和领域逻辑容易混杂。
- 为每个模块建立 workspace 包：物理边界更强，但一期只有一个部署单元，立即引入包发布、构建图和多份配置的成本缺少事实依据。
- 只依赖代码评审约束导入：无法持续发现间接导入、循环依赖和客户端携带服务端代码，不足以支持并行协作。
- 让 OpenAPI 或 ORM 生成类型直接作为领域模型：减少短期转换，但会使传输、存储结构反向控制业务语义，违反既有分层与适配器决策。

## 影响

正面影响：

- 工作包可以按业务模块分配清晰的目录所有权；
- API 契约、运行时边界和业务实现具有明确落点；
- 非法跨模块访问、循环依赖和服务端代码泄漏可以自动验证；
- 未来若拆分服务，模块公开契约和数据所有权可作为评估基础。

成本与约束：

- 跨模块调用需要维护专用公开契约和必要的边界转换；
- 共享代码必须经过语义与所有权判断，不能随意移动到公共目录；
- 工程基础阶段必须建立导入规则和架构测试，目录约定本身不会自动形成边界；
- `public/server` 与 `public/client` 的运行时隔离需要构建检查持续验证。

兼容性方面，本决策只固定内部工程结构，不发布新的业务 API，也不引入运行时兼容层。未来目录迁移必须保持公开入口稳定，或与全部消费方在同一变更中完成并通过架构测试。

## 迁移与验证

当前仓库尚无应用代码、依赖和数据库迁移，因此不进行文件搬迁。工程基础工作包开始后按以下顺序落地：

1. 创建实际需要的 `src` 与测试目录，不批量生成空模块；
2. 建立路径别名、服务端专用保护和依赖边界规则；
3. 为合法导入、跨模块内部导入、反向分层、循环依赖和客户端导入服务端代码分别提供正反测试；
4. 建立 API/生成代码可重复生成检查，但不得在生成产物中补写业务规则；
5. 用首个真实纵向切片验证路由、公开入口、应用用例、领域规则、端口实现和测试命令；
6. 在本地与 CI 执行相同的类型、静态、架构、契约和测试入口后，才允许业务工作包并行编码。

若实际框架验证表明某个目录无法满足 Next.js 运行时约束，应以新的 ADR 修订结构和迁移路径，不得在模块内复制平行业务实现绕过边界。
