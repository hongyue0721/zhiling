# ADR-0010：邮箱验证与会话安全策略

- 状态：Accepted
- 日期：2026-09-02
- 决策者：项目维护者

## 背景

ADR-0007 已要求所有产品能力必须登录，项目目标已选择 Better Auth Email & Password，但会话生命周期、邮箱验证、密码恢复、邮件供应商和失败限制尚未确定。直接采用框架默认值会把未评审策略变成业务事实，也无法证明退出、过期、邮件失败和多实例限流符合安全边界。

哥哥已确认一期默认启用邮箱验证，不实现密码恢复，并选择 Resend HTTP API 发送验证邮件；同时要求部署可以显式关闭邮箱验证。这个开关必须表现为可审计的业务策略，不能用缺失配置、假邮件成功或静默放行掩盖邮箱所有权保证的变化。

## 决策

### 账户与邮箱

- 使用 Better Auth Email & Password，并锁定经过实际测试的精确版本；
- `EMAIL_VERIFICATION_ENABLED` 是服务端必填的 `true`/`false` 策略，示例配置默认
  为 `true`，生产环境必须显式填写；
- 启用邮箱验证时，注册邮箱必须完成验证后才能建立可访问产品能力的正式 Session；
  注册后发送验证邮件，验证 Token 有效期为 1 小时；
- 启用邮箱验证时，验证成功后不自动登录，用户必须显式提交一次登录，并允许显式
  重发验证邮件；两者都必须受限流保护；
- 关闭邮箱验证时，注册仍不自动建立 Session，但正确密码可以直接登录；应用正式
  身份保留 `emailVerified=false`，不伪造已验证事实；
- 邮箱验证关闭时不创建邮件发送器，不要求 Resend 配置，并且不导出验证与重发端点；
- 一期不提供忘记密码、密码重置或邮件找回端点；后续纳入时必须补充 ADR，确认
  Token、邮件、会话撤销和防枚举规则；
- 认证 Route Handler 仅导出 `GET`、`POST`；`PUT`、`PATCH`、`DELETE` 等不支持的
  HTTP 方法由 Next.js 按框架语义返回 `405 Method Not Allowed`。已导出的 `GET`/`POST`
  对允许列表之外的修改密码、修改邮箱、删除账户及插件端点返回空 `404`，不因
  Better Auth 默认路由而意外扩大产品能力；
- 密码长度为 12 至 128 个字符，不增加会导致弱口令模式化的字符组合规则；密码只
  交给 Better Auth 的哈希实现，不进入业务日志或自定义持久化字段。

邮箱验证、登录和注册是未登录访问例外。启用邮箱验证时，未验证邮箱不构成可访问
产品的正式身份；关闭时，有效 Session 可以转换为正式身份，但邮箱验证状态仍按
数据库事实传播到身份对象。

### 邮件供应商

- 启用邮箱验证时使用 Resend HTTP API 作为一期验证邮件供应商；关闭时不初始化
  供应商适配器，也不读取 Resend 配置；
- 身份模块通过自己定义的邮件发送端口调用基础设施适配器，不向应用层暴露 Resend
  DTO 或错误对象；
- 启用邮箱验证时，`RESEND_API_KEY` 与 `AUTH_EMAIL_FROM` 只从服务端配置读取，
  缺失时认证组合根显式失败；
- 验证邮件只包含一次性验证 URL 和必要产品文案，不包含密码、Session Token、
  Access Secret 或内部诊断；
- Resend HTTP 适配器把供应商失败映射为稳定的邮件依赖错误，不读取或返回 Resend
  原始正文；
- Better Auth `1.7.2` 会捕获邮件回调异常而保留已创建的未验证账户，托管端点的
  成功响应只表示账户请求已受理，不表示邮件已送达；启用验证时用户通过显式重发
  流程恢复，产品文案不得宣称投递成功；
- 日志只记录请求关联 ID、邮件操作类别和稳定失败类别，不记录 API Key、验证
  Token 或完整验证 URL。

### Session

- Session 保存在 PostgreSQL，不使用只靠客户端 Cookie 即可长期成立的无状态 Session；
- `expiresIn` 固定为 7 天，`updateAge` 固定为 1 天；活跃 Session 每到续期窗口可把到期时间延长为当前时间加 7 天；
- 允许同一账户在多个设备建立独立 Session，不设置缺少业务依据的硬数量上限；
- 用户可以查看和撤销自己的 Session；普通退出只撤销当前 Session；
- Session 过期或撤销后，下一次页面、HTTP、Server Action 或 SSE 校验必须立即失败；
- 不启用会让已撤销 Session 在 Cookie 缓存有效期内继续成立的 Session Cookie 缓存；
- Cookie 必须为 `HttpOnly`，生产环境必须为 `Secure`，`SameSite=Lax`，路径为 `/`；可信来源使用显式配置，不接受任意 Origin。

### CSRF、限流与失败响应

- 使用 Better Auth 的 Origin/CSRF 防护和安全 Cookie，不自建平行 Token 机制；
- 生产环境通用认证限流为每 IP 每 60 秒最多 100 次；邮箱登录沿用每 10 秒最多 3 次的严格规则；注册与验证邮件发送额外限制为每 IP 每 60 秒最多 3 次；
- 限流状态必须存入 PostgreSQL 或经新决策确认的共享存储，不能依赖单实例内存；
  部署必须显式提供反向代理 IP/CIDR 并限制源站直连，使 Better Auth 从可信转发链解析客户端地址；缺失可信地址而退化为全局共享桶属于部署错误；
- 服务端直接调用 `auth.api` 不受框架客户端限流保护，因此业务代码不得把它暴露成绕过受管端点的公共代理；
- 认证端点错误属于 Better Auth 版本化框架契约，不写成知径业务 OpenAPI；前端只映射稳定、安全的 UI 状态，不通过原始错误字符串驱动业务逻辑；
- 登录失败、重发验证和注册响应不得暴露某个邮箱是否已注册、是否存在 Session 或供应商内部状态。

### 统一服务端身份上下文

身份模块公开的服务端入口只返回最小正式身份：稳定用户 ID、规范化邮箱和邮箱已验证事实。调用方不得接收数据库用户行、Session Token、Cookie 或 Better Auth 内部对象。

页面、Route Handler、Server Action 和 SSE 入口分别调用同一身份解析能力。请求体、查询参数、路径参数及自定义请求头中的用户 ID 永远不能替代 Session 身份。

## 理由

启用邮箱验证避免不可达邮箱成为长期账户事实；显式登录避免验证链接同时变成隐式
Session 建立入口。数据库 Session 与禁用 Cookie 缓存保证退出和撤销立即生效。Resend
通过应用端口隔离，既满足默认的一期邮件闭环，也不让供应商协议控制身份模块。

关闭验证是已确认的部署例外，不是安全默认：它降低邮箱所有权、账户恢复和部分反滥用
保证，但仍保留 PostgreSQL Session、Origin/CSRF、密码策略、限流、资源授权和
`emailVerified` 原始事实。系统不得用未配置的假邮件、万能 Token 或静默成功响应伪装
找回能力。

## 替代方案

- 始终强制验证邮箱：安全保证最高，但无法满足已确认的无邮件部署场景；
- 关闭邮箱验证：实现简单且不依赖邮件供应商，但降低邮箱所有权和反滥用保证，
  因此只允许通过显式配置选择，不能成为默认值；
- 同期实现密码恢复：需要额外确定恢复 Token、防枚举、邮件重放和全 Session 撤销，
  超出确认范围；
- 使用 SMTP：供应商中立，但一期需额外承担连接、TLS 和投递配置，哥哥已选择 Resend；
- 只使用无状态 Cookie Session：撤销与立即失效边界更难证明；
- 限流只存内存：多实例或重启后行为不一致，不能形成安全事实。

## 影响

- C1 必须引入 PostgreSQL、Drizzle、Better Auth 与 Resend 的精确版本及迁移；关闭
  邮箱验证的部署不需要 Resend 密钥，但必须显式记录该策略；
- 未登录例外根据 `EMAIL_VERIFICATION_ENABLED` 增加邮箱验证和显式重发端点，或仅
  保留注册、登录端点；两种模式都不增加密码恢复端点；
- 本地开发需要真实数据库；启用邮件时适配器在测试中使用模块端口的确定性测试
  实现，关闭邮件时测试必须证明不初始化适配器；
- Better Auth 托管端点及数据库 schema 需要随版本锁定并通过契约、集成和迁移测试，
  两种邮箱策略都必须覆盖；
- 后续新增密码恢复、其他邮件供应商、Session 数量上限或无状态缓存时必须重新决策。

## 迁移与验证

1. 锁定 Better Auth `1.7.2`、Drizzle ORM `0.45.2`、Drizzle Kit `0.31.10` 与
   `pg` `8.23.0`，生成并审查 `drizzle/0000_identity_auth.sql`；
2. 契约测试覆盖启用模式的注册、验证、登录、未验证拒绝、退出、过期、重发验证和
   数据库限流策略，以及关闭模式的直接登录和验证端点不暴露；
3. 集成测试使用真实 PostgreSQL，证明两种策略下跨请求恢复同一账户、撤销和过期立即
   生效；
4. 架构测试证明客户端不能导入服务端认证、数据库、Resend 或密钥配置；
5. 安全测试证明响应与日志不含密码、Session Token、验证 Token、完整验证 URL 或
   供应商原始错误；
6. Better Auth `1.7.2` 的 Cookie、Origin、防 CSRF、邮件失败和托管端点行为记录在
   [认证框架契约](../../api/authentication.md)。
