# 文档治理规则

> 状态：协作基线。

## 单一事实源

- 产品定位、一期范围和成功标准：`PROJECT_GOAL.md`；
- 已接受架构选择：`docs/architecture/decisions/`；
- 已发布 HTTP API：`api/openapi.yaml`；
- 业务不变量和模块边界：对应架构文档；
- 用户可见版本变化：`CHANGELOG.md`。

说明性文档不得复制并悄悄改变上层事实。发现冲突时，应修改真正的事实源并同步所有投影，而不是在下游增加“以本文件为准”。

## 状态标记

设计文档必须明确属于以下状态之一：

- **提议**：可以评审，不能作为实现事实；
- **已接受**：已经成为实现和测试约束；
- **已否决**：保留历史但不得实施；
- **已弃用**：曾经生效，正在迁移或等待移除；
- **已替代**：由明确链接的新文档接管。

ADR 使用对应的英文状态值，流转规则以 ADR 索引为准。

## 同步更新门禁

| 变更 | 同一 PR 必须更新 |
| --- | --- |
| 产品范围或业务规则 | 项目目标、需求索引、领域契约、验收场景、CHANGELOG |
| 模块职责或依赖 | 架构总览、模块边界、ADR、所有权说明 |
| HTTP/SSE 契约 | OpenAPI 或事件 schema、示例、错误、兼容登记、契约测试 |
| 数据或事务边界 | 数据模型、ADR、迁移与回滚说明、集成测试 |
| 第三方协议 | 适配器契约、版本、脱敏样本、兼容登记、契约测试 |
| 开发或发布流程 | CONTRIBUTING、对应开发文档、CI 或 PR 模板 |

纯文字修正如果不改变语义，可以只更新错误所在文档；提交说明必须明确它不改变契约。

## API 文档规则

- 实现前或同一变更中先更新机器契约，禁止接口合入后再补文档；
- 每个端点包含身份与授权、请求、成功响应、实际错误码和示例；
- 每个 schema 区分必填、可空、缺失和空集合；
- 破坏性变更必须记录支持期限、迁移方法和移除条件；
- Better Auth 与第三方接口必须依据锁定版本和真实资料，不凭印象抄写。

## 评审与失效处理

- 修改事实源的 PR 至少由受影响模块所有者评审；
- 评审者检查文档描述的命令、路径和链接真实存在；
- 发现过时文档应在当前任务中修复；若超出范围，创建带所有者和验收标准的 Issue；
- 不允许使用永久 `TODO` 代替已知且阻塞实现的决策；未决问题进入提议 ADR 或需求开放问题；
- 删除能力时保留 ADR、CHANGELOG 和退役工作包等必要历史，不复用已发布标识。
