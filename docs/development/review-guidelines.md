# 变更评审指南

评审的目标是证明变更满足已确认业务事实，并且能够被其他成员安全维护和继续演进。代码能运行或当前测试通过，不等于可以合入。

## 进入评审的条件

作者在请求评审前必须完成：

1. 关联已具备目标、范围、非目标和验收标准的 Issue；涉及长期、跨模块或难以回滚的选择时，关联已接受的 ADR；
2. 将实现、测试、API/模块契约和相关文档作为同一变更交付；
3. 完整填写 PR 模板，给出实际执行的命令、环境与结果；
4. 标出受影响的所有权范围，并按[所有权规则](ownership.md)请求评审；
5. 确认自动检查成功。检查尚未完成或失败时可以提前讨论，但不能请求批准或合入。

草稿 PR 可用于尽早确认方向，但不得替代 Issue 或 ADR 的事实确认过程。

## 评审职责

### 作者

- 对业务事实、变更完整性和验证证据负责；
- 回应每条阻塞意见，修复后说明改了什么以及如何重新验证；
- 新提交使既有批准失效时，主动重新请求评审；
- 不自行批准或合入自己的 PR。

### 评审者

- 先核对目标和契约，再检查实现细节；
- 对不确定内容提出问题，不把个人偏好写成强制要求；
- 阻塞时指出违反的事实、契约或风险，并给出可验证的解除条件；
- 不因已有测试为绿色而跳过对测试覆盖范围和断言有效性的审查。

### 受影响范围的所有者

- 确认模块职责、依赖方向、数据所有权和演进策略；
- 公共契约变更必须由提供方和至少一个实际消费方共同评审；
- 兼容层必须确认支持范围、失败语义、观测方式、迁移计划和移除条件。

## 必审维度

### 业务事实与范围

- 行为是否来自 `PROJECT_GOAL.md`、已接受 ADR、已发布契约或明确的人类确认？
- 是否把未知字段、关系缺失或外部失败伪装成成功？
- 改动是否覆盖根因和完整纵向行为，且没有附带无关重构？
- 非目标是否真的没有被悄然实现或封闭？

### 架构与数据一致性

- 模块职责和依赖方向是否符合边界约定？
- 数据由谁创建、更新和判定，是否只有一个事实来源？
- 事务、并发、幂等和失败路径会不会产生半成品、重复记录或关系错配？
- 扩展点是否基于确认需求，而不是为假设场景制造抽象？

### 契约与兼容

- HTTP、SSE、模块、数据和第三方契约是否与实现及示例一致？
- 可空、缺失、空集合、枚举和错误码是否具有明确且一致的语义？
- 破坏性变更是否有版本、迁移窗口、回滚边界及调用方确认？
- 兼容层是否集中、可观测、有测试且有可验证的移除条件？

### 测试与验证

- 核心正常路径、边界和明确失败路径是否都有可读断言？
- 测试是否真正经过公开边界验证行为，而非复制实现细节？
- 契约、迁移、并发、授权或外部适配变化是否有相应层级的测试？
- PR 中记录的命令和结果是否足以让其他成员复现？

### 文档与安全

- 产品、架构、API、开发和变更文档是否与最终行为同步？
- 身份是否从可信会话取得，所有权是否在服务端校验？
- 密钥、令牌、个人数据、正确答案和第三方敏感正文是否可能进入客户端、日志、数据库或提交历史？
- 外部输入和错误响应是否经过校验与脱敏，且不会泄露内部实现？

## 意见等级与处理

评审意见使用以下前缀，避免含义模糊：

- `阻塞`：违反业务事实、架构边界、契约、数据一致性、安全或完成定义；解决前不得合入；
- `问题`：信息不足，回答可能转为阻塞或解除；结论明确前不得忽略；
- `建议`：不影响本次正确性，可由作者接受、解释后拒绝或登记后续任务。

作者不得只用“已处理”关闭意见，应附具体修改位置或可验证说明。评审者确认阻塞条件解除后再解决会话。

## 批准与合入门禁

同时满足以下条件才可合入：

- Issue 的验收标准逐项具有证据；
- 所有受影响范围已按所有权规则获得批准，且没有未解决的阻塞或问题；
- 公共契约的提供方与实际消费方均已确认；
- 自动测试、静态检查、构建及所需契约/迁移检查全部成功；
- 文档与 API 契约已同步，兼容与回滚方案可执行；
- PR 分支已基于最新目标分支完成最终验证；
- 合入者确认提交信息可使用中文完整说明功能、原因和验证结果。

出现以下任一情况必须停止合入：业务依据仍待确认、已接受 ADR 与实现冲突、所有者未分配且未指定临时评审者、存在未解释的测试缺口、迁移不可回滚却未经明确批准，或安全风险尚未闭合。

## 变更后的重新评审

批准后若新增提交影响已评审的业务行为、公共契约、数据迁移、安全边界或测试结论，原批准不再作为合入依据，必须通知相关所有者重新评审。仅修正文案或按评审意见完成不改变语义的机械调整时，可由原评审者明确确认是否需要重审。
