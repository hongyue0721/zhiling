# 并行工作与交接协议

> 状态：协作基线。适用于人类成员和受委派代理。

## 领取工作前

负责人必须先确认：

- 对应 Issue 或工作包具有目标、范围、非目标和可验证验收标准；
- 允许修改的模块或文件范围已经明确；
- 上游契约已接受，不依赖尚未确认的业务事实；
- 与其他进行中任务不存在同一内部文件的高频重叠；
- API、数据、兼容性、安全和文档影响已经列出。

条件不足时先补齐契约或拆分任务，不以“写到哪里算哪里”的方式开始。

## 并行修改规则

- 每个任务只修改被分配的边界；发现跨边界根因时先通知相关所有者；
- 共享契约由提供方发起修改，消费方共同评审后再并行实现；
- 不覆盖、回退或顺手提交其他成员的工作区改动；
- 不复制另一模块的内部类型或规则来规避等待；
- 临时兼容必须登记适用范围、失败语义、负责人和移除条件；
- 分支保持短生命周期，定期吸收 `main` 的已接受契约变更。

## 冲突处理顺序

1. 判断冲突是否说明两个任务拥有同一职责；
2. 若是职责冲突，先调整模块所有权或公共契约；
3. 若只是机械文件冲突，由文件所有者整合，另一方提供最小清晰的变更说明；
4. 若涉及业务事实，暂停相关实现并请求人类确认；
5. 不通过复制文件、增加第二套 schema 或创建隐式适配器绕过冲突。

## 交接内容

任务移交或完成时必须说明：

- 已完成的用户可见能力或架构结果；
- 实际修改的文件与公开契约；
- 实际执行的验证命令和结果；
- 数据、API 和兼容性影响；
- 仍未确认的问题、已知限制和后续依赖；
- 对应提交或 PR，以及需要评审的所有者。

“代码已写完”“应该能用”或只给文件列表不构成有效交接。

## 子代理协作

- 主负责人为每个子代理分配独立、具体且可验证的子任务；
- 共享工作区中的代理修改范围不得重叠，除非明确指定一个最终整合者；
- 子代理不得独立提交或推送，除非任务明确授权；
- 主负责人必须重新检查子代理产出，不能把子代理的自述当作完成证据；
- 最终提交使用统一中文标题和完整功能、原因、验证说明。
