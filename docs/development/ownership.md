# 所有权与评审分配

所有权用于确保受影响领域有人对事实、契约和长期演进负责，不代表个人可以绕过评审独自决定。当前尚未完成团队分工，因此本文不编造姓名、账号或 GitHub 团队；所有责任人均保持“待分配”。

## 角色定义

- **领域所有者**：维护业务规则、领域不变量和验收边界；
- **契约所有者**：维护对外或跨模块契约、版本与兼容策略；
- **实现所有者**：维护模块内部设计、测试和运行质量；
- **临时评审者**：在正式所有者尚未分配时，由仓库维护者在具体 Issue 中明确指定，只对该任务生效。

同一成员可以承担多个角色，但作者不能作为自己 PR 的唯一批准者。公共契约的提供方与消费方不能由一次自审替代共同确认。

## 分配流程

首次开始某个工作包前，仓库维护者必须：

1. 在任务 Issue 中明确领域、契约和实现所有者；
2. 核对人员具有相应事实与边界的上下文；缺少上下文时先安排共同评审，不直接授权；
3. 将稳定分配更新到上表；代码目录出现后同步 `CODEOWNERS`；
4. 通知上下游实际消费方，确认谁参与公共契约评审；
5. 人员或边界变化时更新文档，不让离任或失效账号继续成为唯一门禁。

在正式所有者仍为“待分配”时，任务可以澄清和设计，但不得开始依赖未确认事实的实现。若确需推进已确认范围，仓库维护者必须在对应 Issue 指定临时评审者，并由不同于作者的人完成批准。

## PR 评审路由

作者根据变更内容选择所有适用范围，不能只按文件路径选择：

- 改变用户可见行为或业务规则：产品与对应领域所有者；
- 改变模块职责、依赖方向或跨模块数据流：架构与双方领域所有者；
- 改变 HTTP、SSE、事件、共享类型或数据契约：契约提供方与至少一个实际消费方；
- 改变认证、授权、密钥、隐私或答案保护：安全范围所有者；
- 改变数据库结构、数据归属、事务或迁移：数据范围和受影响领域所有者；
- 新增或变更兼容层：外部适配/兼容、架构及消费方所有者；
- 只改模块内部实现且不改变可观察行为：对应实现所有者。

一个 PR 命中多个范围时必须获得每个范围的批准。所有者缺席时由仓库维护者在 Issue 指定同范围代理评审者；不得为了合入而删除评审范围、让作者自批，或由不了解契约的成员代签。

## 冲突与升级

- 业务文档、ADR、API 契约与实现冲突时停止合入，先修正事实层或重新决策；
- 所有者之间对跨域契约无法达成一致时，创建架构决策 Issue，并通过 ADR 记录选择和后果；
- 发现安全或数据一致性风险时，任何评审者都可以阻塞，不受范围所有权限制；
- 紧急修复也必须有独立评审和验证证据。若正常所有者不可用，应指定临时评审者，并在合入后补做完整复盘和所有权确认。

具体评审方法和合入门禁见[变更评审指南](review-guidelines.md)。
