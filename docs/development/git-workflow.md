# Git 协作流程

仓库使用两级分支：

- `dev` 是日常集成分支。所有功能、修复、测试和文档变更都通过短生命周期分支 PR 合入 `dev`。
- `main` 是发布分支。哥哥和协作者不得直接推送或手动合入 `main`；`dev` 完成 CI 后由 `dev-to-main` Bot 创建并自动 rebase 合入提升 PR。

## 任务拆分

任务描述至少包含：目标、范围、非目标、输入输出契约、依赖、验收标准、测试要求和需要同步更新的文档。

多人并行时优先按稳定模块边界或完整纵向能力拆分。若多个任务必须频繁修改同一内部文件，说明边界尚未稳定，应先调整设计再分工。

## 标准 PR 流程

1. 从最新的 `origin/dev` 创建短生命周期任务分支；
2. 实现代码、测试、契约和文档，提交信息遵循[贡献指南](../../CONTRIBUTING.md)；
3. 在本地执行协作校验：

   ```bash
   scripts/verify-collaboration.sh --base origin/dev --head HEAD
   ```

4. 创建目标为 `dev` 的 PR，填写 PR 模板并请求对应所有者和独立评审者；
5. 等待 `协作规范检查` 和 `工程质量检查` 完成；检查失败或仍在运行时不得合入；
6. 评审通过且检查成功后，维护者只能使用 rebase 将 PR 合入 `dev`；
7. `dev` 产生新提交后，`dev-to-main` Bot 等待该提交对应的两个工作流成功；
8. Bot 创建或复用 `dev` → `main` 提升 PR，并自动使用 rebase 合入 `main`。冲突、检查失败或超时都会停止自动提升，不得绕过；
9. `main` 的推送检查完成后，保留提升 PR、工作流和提交记录作为审计证据。

## 分支与合入禁令

- 任务分支不得从 `main` 创建；必须从最新 `dev` 创建；
- 普通 PR 的目标必须是 `dev`，不得直接创建目标为 `main` 的业务 PR；
- 人工不得直接推送 `dev` 或 `main`，不得使用管理员绕过、强制推送、merge commit 或 squash；
- 只有 `.github/workflows/dev-to-main.yml` 允许在门禁完成后写入 `main`；
- Bot 只负责 `dev` → `main` 提升，不负责替代 Issue、ADR、评审或测试。

GitHub Issue 的状态流转、工作包链接与依赖见[协作任务队列](task-board.md)。由于当前私有仓库套餐不能启用分支保护，平台不能技术上阻止管理员绕过规则；绕过会破坏可追溯性，不属于正常流程。
