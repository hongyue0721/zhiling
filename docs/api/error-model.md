# 业务 API 错误模型

> 状态：基础信封已由 ADR-0009 接受；每个接口的领域错误码随对应 API 契约评审。

机器可读 schema 位于 [`api/openapi.yaml`](../../api/openapi.yaml) 的 `components.schemas` 与 `components.responses`。设计理由见 [ADR-0009](../architecture/decisions/0009-unified-business-api-error-contract.md)。

## 接口维护规则

每个业务操作必须列出它实际可能返回的 HTTP 状态和错误码。引用公共响应只复用结构，不能代替接口级错误说明。

新增错误码时需要同时回答：

- 它对应哪条明确业务或协议事实；
- 客户端是否需要独立处理；
- 是否安全暴露资源存在性；
- 是否允许重试，若允许由什么事实确定等待时间；
- 是否替代旧错误码及旧码的支持期限。

## 校验问题

`issues` 只描述请求输入中可精确定位的问题：

- `path` 使用 JSON Pointer，例如 `/topic` 或 `/answers/0/optionId`；
- `code` 是稳定的小写下划线标识，例如 `required`、`invalid_format`；
- `message` 可以改善可读性，但不能成为客户端分支条件；
- 多个独立输入错误可以同时返回；
- 认证失败、资源不存在和依赖不可用不得伪造为字段问题。

## 安全边界

- 第三方错误先在适配器转换为内部错误类别，再映射业务响应；
- 日志可记录受控内部原因，但 HTTP/SSE 只暴露稳定安全信息；
- 未授权读取是否使用 403 或 404，由访问控制矩阵和具体接口契约决定；
- 不得把“未知错误”转换为看起来可重试或看起来成功的业务状态。
